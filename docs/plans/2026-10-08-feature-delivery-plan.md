## 3. 用户入口与功能范围

安装后，用户在目标项目中请求使用 feature-delivery，并提交如下信息：

```text
使用 feature-delivery，实现用户列表和权限配置。
产品原型：链接 A、链接 B
UI 设计：Figma 链接 C、蓝湖链接 D
接口文档：链接 E、链接 F
补充：使用当前项目已有组件；本次只修改用户管理模块。
```

不强制用户填写表格或先手动关联页面和接口。用户可以提供普通自然语言；Agent 负责归类来源并生成内部工作规格。

支持三个任务形态：

1. 单功能：多个来源共同描述一个功能。
2. 多功能：同一批来源包含多个功能，共享或独立的接口、组件及流程。
3. 补充修改：在现有功能上依据新的原型、设计或 API 变更实施，先核对当前代码和新资料。

## 4. 执行流程

### 阶段 A：目标项目适配

读取适用的 AGENTS.md、用户要求和被引用的项目规范；检查工作区现有修改。识别技术栈、包管理器、路由、组件库、样式方案、接口层、鉴权方式、国际化和现有验证入口，按当前功能读取相关部分。

输出紧凑的项目上下文：目标目录、可复用组件和请求封装、允许的检查方式，以及影响实施的约束。不得让设计工具生成的默认框架代码覆盖项目实际技术栈。确认是已有前端项目；无法确定项目或用户要求从零创建时，说明第一版边界并询问后续处理。

查找该项目已有的任务记录目录设置；首次使用时询问用户保存目录，收到答复后持久化选择。建议使用项目根目录 `.feature-delivery.json` 作为轻量索引，只保存 `schemaVersion` 和 `recordsDir`，项目内目录优先保存为相对路径；目标项目另有配置约定时沿用该约定。该索引是实施建议，不得改写既有同名配置或在用户尚未选择目录时预设位置。具体任务与业务信息保存到所选目录，不写入全局 Skill。

### 阶段 B：来源登记与能力检查

按内容和平台识别来源，不以单个 URL 标记或页面标题代替内容判断。检查当前可调用工具、认证及读取权限，优先复用已有连接。

每个来源独立记录：sourceId、来源类型、平台、URL、页面或节点 ID、版本或读取时间、读取状态、相关内容及缺口。失败与重试只影响该来源，保留其他来源结果。

推荐路径：Figma 使用官方设计上下文、截图、素材及当前可用的原型交互读取能力；蓝湖使用经过验证的 MCP 需求文档及设计稿工具。API 默认优先采用 YApi 的现有连接、网页或导出路径；OpenAPI/Swagger 读取结构化定义；其他动态网页采用可用浏览器读取。平台支持表示可选择读取路径，不能把未实测平台声称为已验证兼容。

缺少 Figma 或蓝湖 MCP 时，提醒用户并按当前客户端和操作系统逐步引导安装、认证及连接验证。认证信息由用户在本地完成。普通功能开发请求不静默安装或改写全局连接配置，不替换现有服务或升级运行时。

### 阶段 C：按功能读取与关联

先索引页面和节点，再围绕目标功能读取必要细节，避免一次拉取整个设计项目和接口站点。明确区分页面列表、截图、业务注释、交互及接口结构。

产品资料提取角色、业务实体、页面入口、操作、权限、校验与状态流转。UI 提取布局、组件、样式、素材和可见状态。API 提取方法、路径、参数位置、响应包络、枚举、分页、错误码和鉴权要求。

读取充分性按本次功能判断：链接能打开、工具握手成功、拿到页面列表或截图，都不能代替交互、业务说明和接口字段的读取。原型交互、UI 状态及素材或 API 必需契约缺失时，说明具体缺口并引导用户补充。不能把只有截图的结果标记为已完整理解原型。

基于业务对象、字段、操作和流程建立关联；名称只作为线索。每个功能可以引用多个来源，每个来源也可以被多个功能使用。

### 阶段 D：形成实施规格

每个功能规格包含：

- featureId、名称、实施范围及关联来源。
- 页面、路由、入口、角色权限及关键交互。
- UI 节点与复用组件。
- 接口、触发时机、参数、字段映射、枚举转换和响应处理。
- 加载、空数据、失败、无权限与重复提交等适用状态。
- 共享依赖、拟修改文件、验收场景及资料缺口。

范围依据用户本次描述；功能及交互依据产品原型；样式依据 UI 设计；请求契约依据 API 文档。原型的简化样式与 UI 提供的完整视觉细节无需确认。上述职责不能用来跳过真实冲突：原型、UI 或 API 对操作、字段、权限、业务流程等给出互不兼容要求时，必须询问用户，不自行选择一份资料裁决。

冲突问题必须包含双方的来源及页面或节点、具体要求、冲突位置、影响的实现及可供用户选择的处理建议。建议不是最终决定；收到用户明确答复后记录决策，再继续实现。等待期间暂停整个任务的实现，不以其他功能独立为由继续写业务代码；记录当前进度及恢复点。

资料没有说明权限、删除恢复、金额取整、业务校验或状态流转等关键业务规则时，同样暂停整个任务并询问用户。加载、空数据、请求失败等通用状态默认补齐，优先复用项目现有实现。无权限状态的视觉展示可以复用，但角色权限本身不能据此猜测。

将规格写入该项目已选择的记录目录，每次迭代新增独立记录。内容包括用户本次描述、关联来源与版本或读取时间、功能及接口映射、用户决策、改动范围、验证结果和未完成项。后续迭代读取既有记录并核对当前资料及代码，旧记录不能代替新资料。敏感凭据及携带凭据的链接参数不进入记录。用户要求持久化的记录属于交付物，代理的其他临时过程文件按项目规则清理。

### 阶段 E：实施

按依赖处理共享类型、请求层和组件，再实施功能；避免为了抽象复用而提前改动无关模块。多个功能分别保留改动范围及验收条目。

遵循当前会话与项目的修改授权和审查流程。已有明确实施授权时不逐步骤重复询问；有明确的先看 diff 后写入要求时按该要求执行。

第一版只修改用户描述范围内的前端代码及接口接入。已完成资料读取、范围明确且无冲突时直接实施，不额外要求确认整份规格。中途发现真实冲突或关键业务信息缺失时进入全任务等待状态，收到用户答复再恢复。

### 阶段 F：验证与交付

默认使用项目开发环境进行真实浏览器、网络请求及接口响应验证，优先复用已有可用开发服务。需要登录、测试账号或访问权限时，明确说明阻碍并引导用户登录或授权，等待后继续。只有用户明确选择跳过时才停止相应验证，并提供可执行的手动步骤、预期结果及未验证项；不得以等待超时或 Mock 通过作为跳过授权。

项目未明确限制时，允许运行适用的类型检查与生产构建，优先使用项目既有命令；项目或用户有明确限制时按限制执行。检查范围与当前改动相称。

验证失败先检查任务开始时的工作区状态、可用基线和本次 diff，判断是否由本次改动引起。本次引入的问题在任务范围内修复；项目原有问题记录证据和影响，需要扩大修改范围时询问用户。无法判断归因时说明证据不足，不直接宣称为既有错误，也不展开无关修复。

逐功能报告：已实现、静态检查、交互验证、视觉核对、Mock 验证、真实接口联调、阻塞项。Mock、截图或格式验证不能代替真实联调及浏览器验收。

## 8. 实施任务与验收

### 任务 1：主流程、项目适配和映射规范

文件：SKILL.md、project-adaptation.md、source-reading.md、feature-mapping.md、agents/openai.yaml。

执行：写明准确触发条件；建立功能规格和读取状态；描述关键歧义处理；补齐项目适配；按需路由参考文件；按元数据指南创建 Codex 展示信息。

### 任务 3：交付验收规范与行为评测

文件：acceptance.md；评测使用隔离样例及脱敏资料。

执行：评测最小真实场景并比较使用 Skill 前后的行为；进行功能关联、项目适配与缺口处理评测。工具不可用的路径可模拟失败条件，但不得以模拟结果声称真实平台接入成功。

验收场景：

1. 两个原型、两份设计、三份接口资料描述同一个功能，能形成正确关联。
2. 一组来源描述多个功能，共享接口识别正确，实施范围清楚。
3. 同名页面分别属于不同来源，不能错误合并或覆盖。
4. 原型与 API 枚举矛盾，说明来源、位置和影响，暂停整个任务；其他独立功能也不继续实施。
5. 一个来源无权限，保留其他来源结果并引导用户授权；缺少关键内容时不将任务标记为资料完整。
6. Vue 与 React 两个目标项目分别沿用自己的组件、路由和请求层。
7. 项目禁止构建或要求先确认 diff，Skill 遵守当前规则。
8. Mock 通过但无测试环境，引导用户提供环境；未经明确选择不能跳过真实验证。
9. 用户明确选择手动验证，交付未验证项、步骤和预期结果，不报告为已通过。
10. 链接包含多个功能但用户只要求小迭代，只实施描述范围内的改动。
11. 项目没有限制时可运行类型检查和构建；验证失败区分本次问题、既有问题及归因不明。
12. 原型简化样式与 UI 完整视觉细节互补，按原型实现功能、按 UI 实现样式。
13. 资料缺少删除恢复或金额取整等业务规则，暂停整个任务并询问；通用加载和错误状态默认补齐。
14. 首次选择记录目录后，后续沿用；每次任务新增记录并保留来源版本及用户决策。
