# 项目适配与任务记录

## 项目上下文

确认当前目录属于用户指定的已有前端项目。空目录不生成脚手架；目标不清楚先问用户。读取适用的 `AGENTS.md`、用户要求、项目引用的规范以及相关目录规则。

检查 Git 工作区并记录本次开始时的修改。仅读取当前功能相关的目录、依赖声明及锁文件，识别：

- 框架与版本、包管理器、项目声明的运行时；
- 路由、组件库、主题 token、样式方案和国际化；
- 请求层、响应包络、鉴权、错误处理、分页和字段约定；
- 相似页面、公共交互、开发服务和相关检查命令。

遵循已有结构。设计工具默认输出的框架、utility class、组件包只是参考；不能因此切换技术栈或新增一套设计系统。需要新增依赖时先核对必要性、项目版本和规则，不自动切换 Node/Python 或升级现有依赖。

资料完整且无冲突时直接实施。当前任务明确实施授权优先于无关工作流的额外审批；明确存在的项目修改约束仍应遵守。不把一个项目的规范复制进全局 Skill。

## 首次选择记录目录

1. 查找项目已有 `feature-delivery` 目录设置；优先读取项目根目录 `.feature-delivery.json` 或项目明确规定的对应设置。
2. 首次没有设置时，先询问用户：“这个项目的功能交付记录保存在哪个目录？这些记录会作为后续迭代资料长期保留，之后一直沿用该目录。”收到目录答复前不开始实现，也不自行选一个目录先写任务资料。目录选择同时明确记录的交付用途；项目对临时文档的清理规则仍适用于其他代理过程文件。
3. 核对路径归属与可写性。不存在的目录可按用户选择创建；目录存在时保留原文件。项目内路径保存为相对项目根目录路径，用户选择外部目录时保存明确的绝对路径。
4. 项目没有其他配置约定时，新建 `.feature-delivery.json` 作为目录索引，只存设置，不存业务资料或凭据。已有同名文件格式不兼容、目录不可用或不同规则冲突时询问用户，不能覆盖或换位置。
5. 后续读取该设置并沿用，不重复询问。用户明确要求更换目录时更新设置，旧记录保持原状，迁移另按用户要求处理。

以下是用户已经选择 `docs/feature-delivery` 后的配置示例，不是自动采用的默认目录：

```json
{
  "schemaVersion": 1,
  "recordsDir": "docs/feature-delivery"
}
```

## 每次任务独立记录

使用当前本地时间和简短任务名建立唯一文件，例如 `YYYY-MM-DD-HHmmss-status-filter.md`；同名时加后缀，不能覆盖。更新本次文件的进度与结果，后续迭代新建文件。记录按首次目录选择时说明的用途长期保存；若项目对持久化另有冲突规则，先询问，不自行把任意过程文件标记为交付物。

记录结构：

| 内容 | 必须记录 |
| --- | --- |
| 任务 | 用户本次描述、功能范围、任务时间、当前状态 |
| 项目 | 目标目录、技术栈、有关规则、开始时工作区状态 |
| 来源 | 独立 sourceId、类型、平台、页面/节点、脱敏链接、版本或读取时间、读取充分性 |
| 映射 | 功能、交互、UI 节点、接口、参数及字段转换 |
| 决策 | 具体冲突或业务缺口、来源位置、用户原意、答复时间、适用范围 |
| 实施 | 修改文件、实现范围、暂停点及待恢复动作 |
| 验证 | 实际命令与结果、浏览器/接口证据、失败归因、用户选择跳过的具体项与手动步骤 |

状态可以是 `reading`、`awaiting_decision`、`implementing`、`validating`、`awaiting_access`、`delivered`、`delivered_with_unverified_items`。`delivered_with_unverified_items` 需要用户明确选择跳过受阻验证；不是 Agent 自行结束的出口。

后续迭代先查相关记录，再核对当前来源、接口和代码。过去的决定可以避免重复询问同一问题，但资料变更导致决定不再适用时，应提出新的具体问题，不能静默沿用旧规则。

记录中不包含 Cookie、Token、账号密码、私密请求头或业务响应中的敏感个人信息。链接含签名、Token 等参数时脱敏，保留足以定位资料的非敏感标识；访问能力留在本地连接配置中。
