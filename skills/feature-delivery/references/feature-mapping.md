# 功能关联与用户决策

## 范围与来源关联

把用户描述拆为本次功能或小迭代，再关联来源中的业务对象、操作、字段与流程。页面/接口名称只能辅助判断。已有功能只改本次相关部分，资料中的其他模块不自动纳入范围。

每个功能形成紧凑规格：

| 项目 | 内容 |
| --- | --- |
| 范围 | featureId、用户目标、本次涉及页面与改动边界 |
| 原型 | sourceId、页面/节点、业务操作、权限和校验依据 |
| UI | sourceId、画板/节点、布局、样式、素材及状态 |
| API | sourceId、方法/路径、触发时机、请求参数、响应与错误处理 |
| 字段映射 | 界面字段到请求/响应字段、枚举、单位、分页与空值转换 |
| 实施 | 可复用代码、拟修改文件、共享依赖和实施顺序 |
| 验收 | 真实交互、视觉、请求与响应的可观察结果 |
| 决策 | 资料缺口、冲突、用户答复及对应来源版本 |

字段转换要有明确契约或用户确认。`enabled/disabled` 与 `1/0` 的命名本身不能证明业务映射；展示文案和接口枚举也不能互相替代。

## 互补、冲突与缺失

| 情况 | 行动 |
| --- | --- |
| 原型使用灰框，UI 给出完整色彩和排版 | 功能按原型、样式按 UI，无需确认纯视觉互补 |
| 原型按钮提交，UI 描述为进入审批 | 实际交互冲突，暂停整个任务并询问 |
| 原型要求某字段或枚举，API 不接受或含义不同 | 契约冲突，暂停整个任务并询问 |
| 资料没写删除恢复、角色权限、金额取整或业务状态 | 关键业务缺失，暂停整个任务并询问 |
| 资料没画加载、空数据、请求失败 | 默认补齐，复用项目已有组件和反馈方式 |

不能用“功能按原型、样式按 UI、API 是真实契约”的职责划分来裁决实际冲突。项目旧实现与本次资料存在业务矛盾时，解释差异并询问，也不能以旧代码为默认裁决。

## 全任务等待

发现真实冲突或关键业务缺失时：

1. 停止整个任务的实现，将本次记录更新为 `awaiting_decision`，保留已完成改动与恢复点。
2. 向用户提出具体问题。包含原型、UI、API 中有关来源的页面/节点/接口位置，双方内容、对实现和验收的影响，以及有依据的建议。
3. 等待明确答复。独立功能、共享类型、接口封装、表单骨架也不继续实现；时间压力与交付期限不构成例外。
4. 将用户决定和适用范围写入本次记录，检查是否仍有未决事项。全部影响实现的问题解决后再恢复。

问题示例：

> 原型 P1 的“编辑用户”页要求保存后直接刷新列表；UI U2 的确认弹窗说明为“提交审批”；API A1 的更新接口仅返回保存成功，没有审批信息。这会改变按钮行为和成功提示。此次应直接保存，还是走审批？如果走审批，需要补充对应接口说明。

可以一次列出同一处逻辑的有关差异，减少重复问询。建议供用户评估，不能先按建议落码再请求确认。收到含糊答复不能当作解决；继续指出还缺哪个决定。

用户可以明确重新划定任务范围，例如将有冲突的编辑功能延期、只做导出。记录该用户决定并检查新范围是否仍依赖未决事项，再按新范围恢复。Agent 不得自行拆分范围来绕过全任务等待；交付期限也不能当作用户已作出范围决定。

## 进入实施

用户描述、资料与已确认决策足够后直接实施，不增加整份规格审批。按当前项目组件、路由、请求和样式实现，默认补齐通用状态与已有项目约定的可访问交互。改变权限或业务规则不能归入“通用补齐”。

第一版仅前端及已有接口接入。API 无法满足需求时将问题交给用户，不在服务端补一个接口或虚构地址。需要扩大修改范围时同样询问用户。
